# 10-19-http-semantics-mcp 题目文档（HTTP 语义判定 MCP Server）

> **性质**：不参赛项目题（模拟项目），发布 GitHub **公开仓库**，署名 `yuluo554`。
> **产出仓库**：`10-19-http-semantics-mcp`。
> **版本史**：v1（2026-10-17 定稿；检索基准日 2026-10-17，实测窗口见 §1.2）。
> **交付形态**：**MCP Server（Model Context Protocol，stdio 传输）**——可被 Claude Code / Codex / 任何 MCP 客户端以 tool 方式调用。不设 GUI、不做桌面程序、不做 Web 服务，形态唯一。
> **定位宣言**：
> **"把 Fetch Standard 的 CORS 协议算法与 RFC 9111 缓存新鲜度算法编译成可调用的 oracle：给一组请求/响应头，返回 `allow|block`、违反的规则编号 + 规范条款、以及该改哪个 header。不联网、不抓包、不做安全打分——它回答的是『浏览器会不会放行』『这份缓存还能不能用』，而不是『这个站安不安全』。"**
> **与抓包/代理类工具的区分（本题的题眼）**：`powhttp-mcp`（83★）与 `mitmproxy-mcp`（129★）需要**真实抓包**才能工作，产出是流量回放与观察；本题**不接触任何真实请求**，输入是调用方给的一组 header 字面量，输出是**按规范推导的判定**。判定器是纯函数：同输入 → 字节级相同输出，可被写进测试用例，也可被 AI agent 在写代码前直接问一句"这样配 CORS 会不会被浏览器拦"。

## 一、介绍

### 1.1 问题：CORS 与缓存语义是最容易"看起来对"的两块 HTTP 语义

这两类问题的共同点是：**出错时不报错，只表现为行为异常**——接口在 curl 里通、在浏览器里被拦；缓存明明配了 `max-age` 却每次都回源；`Vary` 写了一个字段却始终 miss；`If-None-Match` 写了但服务端永远回 200。

HN 上的原话（✅ 已核对）：

- 《CORS, the good parts》（**931 分 / 355 评论**；2026 年重发仍 **388 分 / 268 评论**）中，作者原话：
  > "Something about CORS and the resources out there makes newcomers think that it's something the client has to do differently."
  > https://news.ycombinator.com/item?id=20404578 （重发：https://news.ycombinator.com/item?id=48614844 ）
- 同一帖中对动态 `Access-Control-Allow-Origin` 的评论：
  > "Dynamic Allow-Origin … This is super tricky and nonstandard usage that is only necessary to workaround the fact that browsers do not support multiple values on the Allow-Origin header even though the spec allows it."
- 《ETag》相关讨论（**152 分**）中，最高赞评论直接质疑文章给出的实现：
  > "How is the sample `calculateETag()` function generating a weak ETag? It looks like it will generate a different hash due to any JSON formatting changes."
  > https://news.ycombinator.com/item?id=39996521
- 《Cache-Control` semantics》（**197 分 / 71 评论**）：https://news.ycombinator.com/item?id=11679211

共同诉求不是"再讲一遍原理"，而是**能不能给我一个确定的判定**：这组 header 到底放不放行、这份缓存到底还能不能用。

## 二、任务要求（首期 5 个 tool）

> 首期范围严格限定为 T1–T5。每个 tool 的"输入 / 输出 / 确定性纪律"即验收口径，缺一不算完成。
> **数值口径一处定义**：`code` 枚举、`spec_ref` 格式、排序规则、时间解析规则只在 `data/README.md` 第四节定义一次；本文只引用，不复写第二份。

### 模块 T1：`cors_evaluate` —— 单次请求的 CORS 判定

- **输入**：
  - `method`：HTTP 方法名（大写比较，不区分大小写输入）；
  - `origin`：请求的 Origin（字符串，或 `null`）；
  - `url`：目标 URL（只解析 scheme / host / port，用于 same-origin 判断，**不发起请求**）；
  - `credentials`：`omit` | `include`；
  - `request_headers`：对象（header 名 → 值；同名多值用数组表示，保序）；
  - `response`：`{status: int, headers: 对象}`；
  - `is_preflight`：布尔。
- **输出**：
  - `decision`：`allow` | `block`；
  - `violations[]`：`{code, spec_ref, detail}`，按 `code` 字典序稳定排序；
  - `missing_headers[]`：缺失且必要的响应头名（大写规范名，字典序）；
  - `recommended_headers{}`：建议补充/修改的 header 名 → 建议值（键按字典序）；
  - `notes{}`：至少含 `wildcard_with_credentials`（布尔）、`allow_credentials_null_origin`（布尔）。
- **引擎**：按 Fetch Standard 的 CORS 协议算法逐步判定（safelisted 判定、preflight 触发条件、`Access-Control-Allow-*` 校验、credentials 与 `*` 的互斥、`null` Origin 的 `Allow-Credentials` 处理）。规则编号与规范条款的映射表随包发布。
- **确定性纪律**：纯函数；不读系统时钟、环境变量、网络；header 名大小写不敏感、值按规范做 trim 后比较；输出不含自然语言判定（`detail` 为固定模板字符串，模板键由 `code` 决定）。

### 模块 T2：`cors_simulate_fetch` —— 多跳与重定向的逐步判定

- **输入**：T1 全部字段 + `mode`（`cors` | `no-cors` | `same-origin`）+ `redirects[]`（每项 `{url, status, headers}`）。
- **输出**：
  - 逐跳判定：每一跳的 `decision` 与 `violations[]`（结构同 T1）；
  - `final_type`：`basic` | `cors` | `opaque`；
  - `visible_headers[]`：调用方最终可见的响应头名（按 CORS 暴露规则过滤后，字典序）；
  - `preflight_occurred`：布尔；
  - `preflight_cache_key`：字符串（由 origin + url 的 scheme/host/port 派生的稳定键）；
  - `max_age_effective`：整数秒；
  - `events[]`：**重定向必须显式输出事件**——`origin_set_to_null`（跨源重定向后 Origin 置为 `null`）与 `credentials_dropped`（跨源重定向后 credentials 被丢弃），事件按发生顺序排列。
- **引擎**：在 T1 的判定器之上串接重定向语义；`no-cors` 与 `same-origin` 模式走不同的可见性与拦截规则。
- **确定性纪律**：同 T1；`preflight_cache_key` 的派生方式固定（见 `data/README.md` §4）；`events[]` 顺序固定，不因 header 输入顺序变化而变化。

### 模块 T3：`cache_evaluate` —— 缓存新鲜度与动作判定

- **输入**：
  - `request_headers`；
  - `response_headers`；
  - `stored`：`{stored_at, age, headers}`（`stored_at` 为 ISO 8601 字符串）；
  - `now`：ISO 8601 字符串（**允许注入假时钟**，这是本题可测试性的关键）。
- **输出**：
  - `freshness_lifetime`：整数秒；
  - `current_age`：整数秒；
  - `is_fresh`：布尔；
  - `action`：`serve` | `revalidate` | `miss`；
  - `stale_while_revalidate_window`：整数秒（未声明为 `0`）；
  - `must_revalidate`：布尔；
  - `reasons[]`：`{code, spec_ref, detail}`，按 `code` 字典序排序，**每条带 RFC 9111 条款**。
- **引擎**：按 RFC 9111 计算年龄与新鲜度（`Age`、`Date`、`Cache-Control: max-age` / `s-maxage` / `no-cache` / `no-store` / `must-revalidate` / `stale-while-revalidate`、`Expires`、启发式新鲜度），再给出动作。
- **确定性纪律**：**禁止读系统时钟**，`now` 一律入参；时间解析只接受固定格式子集（见 `data/README.md` §4），解析失败按用法错误返回，不做猜测性容错。

### 模块 T4：`conditional_evaluate` —— 条件请求的优先级判定

- **输入**：
  - `method`；
  - `request_headers`：可含 `If-Match`、`If-None-Match`、`If-Modified-Since`、`If-Unmodified-Since`；
  - `resource`：`{etag, last_modified}`（均可为 `null`）。
- **输出**：
  - `status`：`304` | `412` | `200`；
  - `rule_applied`：RFC 9110 §13 优先级中的规则名（固定枚举，如 `if_match` / `if_unmodified_since` / `if_none_match` / `if_modified_since` / `none`）；
  - `weak_comparison_used`：布尔（`If-None-Match` 用弱比较，`If-Match` 用强比较）；
  - `explain[]`：固定模板字符串数组（每条由 `code` + 参数渲染，不是模型生成）。
- **引擎**：按 RFC 9110 §13.2.2 的**求值顺序**实现：`If-Match` → `If-Unmodified-Since` → `If-None-Match` → `If-Modified-Since`；前一条件命中即短路，`rule_applied` 记录真正决定结果的那一条。
- **确定性纪律**：ETag 强弱前缀 `W/` 的解析固定；弱比较与强比较分开实现，不得混用；`Last-Modified` 只做秒级比较。

### 模块 T5：`vary_match` —— Vary 命中判定

- **输入**：
  - `cached`：`{vary, request_headers_at_store}`；
  - `incoming`：`{request_headers}`。
- **输出**：
  - `match`：`hit` | `miss`；
  - `differing_headers[]`：导致 miss 的 header 名（规范名，字典序）；
  - `normalized_vary[]`：去重、排序、大小写归一后的 Vary 字段名列表。
- **引擎**：按 RFC 9111 的缓存键与 `Vary` 语义比较（`Vary: *` 视为永不命中；缺失字段按空值比较；字段值按规范做空白归一）。
- **确定性纪律**：归一化规则固定（trim + 折叠内部连续空白 + 大小写策略按字段类型）；`normalized_vary` 排序固定；同输入双跑字节一致。

### 2.6 统一确定性纪律（五个 tool 共同适用）

1. **纯函数**：禁止读系统时钟、环境变量、文件系统、网络；时间一律入参（T3 的 `now`）。
2. **无 LLM 生成的自然语言判定**：输出只含 `code` + `spec_ref` + 结构化字段；`detail` / `explain` / `reasons` 的文案是**固定模板**，键由 `code` 决定，不调用任何模型。
3. **稳定排序**：`violations[]` / `reasons[]` 按 `code` 字典序；header 名列表按规范名（小写）字典序；`events[]` 按发生顺序。排序规则只在 `data/README.md` §4 定义一次。
4. **字节级可复现**：同一输入连续调用两次，序列化输出逐字节相同（键顺序固定、无时间戳、无随机数、无进程信息）。
5. **每个 `code` 至少 1 条 golden case**：golden case 是仓库内 JSON 文件，输入与期望输出成对冻结；新增 `code` 必须同时新增用例。
6. **发布前跑通 WPT `cors/` 全量映射**：`cors/` 目录下可转写的用例全部映射为 golden case；不可转写的用例逐条登记原因（见 `data/README.md` §2）。

## 六、边界与非目标

- **不做安全扫描**：不检查漏洞、不做 header 安全评级、不做 CVE 关联、不做 HSTS 评分、不做 CSP 评估。本领域已有大量安全头扫描工具（`mcp security` 方向供给充足），**本题主动切割**，只做"浏览器会不会放行 / 缓存还能不能用"的语义判定。
- **不做抓包 / 代理 / 流量重放**：不接管端口、不读 pcap、不解析 HAR。相邻形态（`mitmproxy-mcp` 129★、`powhttp-mcp` 83★）已覆盖该动作。
- **不做真实网络请求**：零 DNS、零 TCP、零 HTTP。`url` 只用于解析 scheme/host/port。
- **不替代浏览器**：判定是**规范推导**，不是浏览器实测。规范与浏览器实现存在差异时，以规范为准并在 `detail` 中注明；不声称"浏览器一定如此"。
- **不做 header 安全评分**：输出中没有分数、没有等级、没有"安全 / 不安全"结论。
- **隐私红线**：纯本地、零网络、零遥测；不落盘用户输入（除非调用方显式要求写 golden case）。
- **品牌隔离**：本题是 HTTP 协议语义判定；文档、仓库名、tool 名不引用本系列其他项目的名称、路径、素材或文档模板。
- **首期范围限定**：只做 CORS / 缓存新鲜度 / 条件请求 / Vary；**不做** CSP、COOP、COEP、HSTS、Permissions-Policy。
- **不编造**：不写无法核对的文号、数值、日期；检索计数与星数一律与基准日 2026-10-17 成对出现；规范条款以发布版原文为准（条款号核对状态见 `data/README.md` §4）。
