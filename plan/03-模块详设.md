# 03 模块详设（T1–T5 判定层）

> 定稿日：2026-10-18（M0 设计），实现随 M2–M4 落地。
> **口径唯一出处**：`code` 枚举、`spec_ref` 格式、排序规则、时间解析、序列化、错误契约一律见 `data/README.md` §4。本文只写**算法步骤与数据结构**，不复写取值。

## 零、共同约定（五个 tool 都适用）

### 0.1 输入规范化（不做"聪明猜测"）

1. header 名：`str.lower()` → 去首尾空白 → 校验 `^[a-z0-9!#$%&'*+.^_`|~-]+$`（RFC 9110 token 字符集）；非法 → `INVALID_HEADER_NAME`。
2. header 值：去首尾 OWS（空格 / 制表）；保留内部空白；**大小写不归一**（值大小写敏感，如 ETag、origin 主机名）。
   例外：`data/README.md` §4.3 第 2 条规定**输出时** header 名统一小写，不影响比较语义。
3. 同名多值：输入用数组表示，**保序**；比较时按规范语义展开（如 `Access-Control-Allow-Origin` 取首个有效值，`Vary` 按逗号拆分）。
4. 方法名：`str.upper()`；不在 `GET/HEAD/POST/PUT/DELETE/PATCH/OPTIONS` 内 → `UNSUPPORTED_METHOD`（M2 实现时按 RFC 9110 §9 的完整方法表校验，枚举进 `codes.json` 旁表）。**测试专用方法**：`TEST-METHOD` 一类如出现，按 `UNSUPPORTED_METHOD` 拒绝，不静默放行。
5. `url`：只解析 `scheme://host[:port]`，不 follow、不 DNS。缺 scheme 或 host → `INVALID_INPUT`。

### 0.2 输出装配（统一）

```python
result = {
    "decision": "allow" | "block",
    "violations": [...],       # 按 code 字典序
    "missing_headers": [...],  # 小写、字典序
    "recommended_headers": {}, # 键字典序（序列化时由 canonical 保证）
    "notes": {...}
}
```

- `violations` 的 `detail` 由 **模板表** 渲染：模板与参数都是冻结常量（`references/codes.json` 的 `template` 字段），参数来自判定过程，**不含自由文本**。
- `recommended_headers` 只放"补什么值"的可执行建议；同一 header 只出现一次。
- `notes` 的键也是冻结枚举（M2 起在 `codes.json` 的 `notes` 段登记），不临时起名。

### 0.3 判定层纪律（AST 守门钉住）

| 禁止 | 检测方式 | 理由 |
| --- | --- | --- |
| `import time` / `datetime` / `random` / `secrets` | AST | 确定性 |
| `import socket` / `ssl` / `http` / `urllib` / `requests` | AST | 零网络 |
| `import os` / `subprocess` / `sys`（判定层） | AST | 环境与进程面 |
| `open(...)` / `Path.read_text` | AST | 不落盘、不读盘 |
| f-string 拼 `detail` | 人工评审 + 模板覆盖测试 | 保证文案可回归 |

## 一、T1 `cors_evaluate`

### 1.1 算法顺序（固定，不因输入顺序变化）

```
S1  规范化输入；same_origin = (origin == None) or origin == url 的 origin
S2  若 is_preflight: 走 P1..P6；否则走 A1..A5
S3  组装 violations / missing_headers / recommended_headers / notes
```

**请求侧（A 分支）**

| 步 | 判据 | 产出 |
| --- | --- | --- |
| A1 | 非 simple 方法（非 `GET/HEAD/POST`）或含非 safelisted 请求头，且 `is_preflight == false` | `CORS_PREFLIGHT_REQUIRED` |
| A2 | 响应无 `Access-Control-Allow-Origin` 且非同源 | `CORS_MISSING_ALLOW_ORIGIN`，`missing_headers += access-control-allow-origin` |
| A3 | `Allow-Origin` 为 `*` 且 `credentials == include` | `CORS_WILDCARD_WITH_CREDENTIALS`；建议回显具体 Origin |
| A4 | `Allow-Origin` 非 `*` 且与 `origin` 不逐字节相等（大小写与尾斜杠按规范比较，见 1.3） | `CORS_ORIGIN_MISMATCH` |
| A5 | `credentials == include` 且无 `Access-Control-Allow-Credentials: true` | `CORS_MISSING_ALLOW_CREDENTIALS` |
| A6 | `origin == null`（字面量 `null`） | `CORS_NULL_ORIGIN` + `notes.allow_credentials_null_origin` |

**预检侧（P 分支）**

| 步 | 判据 | 产出 |
| --- | --- | --- |
| P1 | 响应缺 `Allow-Origin` | `CORS_MISSING_ALLOW_ORIGIN` |
| P2 | `Allow-Origin` 不匹配（同上） | `CORS_ORIGIN_MISMATCH` |
| P3 | 缺 `Allow-Methods` 或不含请求方法 | `CORS_MISSING_ALLOW_METHODS` |
| P4 | 非 safelisted 请求头未列在 `Allow-Headers`（`*` 不覆盖 `Authorization`） | `CORS_MISSING_ALLOW_HEADERS` |
| P5 | 请求头未覆盖（逐头判定） | `CORS_DISALLOWED_HEADER_NOT_EXPOSED` |
| P6 | `*` + credentials（同 A3） | `CORS_WILDCARD_WITH_CREDENTIALS` |

> `CORS_MODE_OPAQUE` 属于 T2 的 `no-cors` 分支；在 T1 出现时按 **note 而非 violation** 输出（`data/README.md` §4.1 已注明）。

### 1.2 safelisted 规则（实现按 Fetch Standard 算法锚点，不做近似）

safelisted 方法：`GET` / `HEAD` / `POST`。
safelisted 请求头（含值约束）：`accept` / `accept-language` / `content-language` / `content-type`（仅 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`）/ `range`（简化）。
`Authorization` **永不** safelisted。

### 1.3 origin 比较

- `origin` 与 `Allow-Origin` 均按 `scheme://host[:port]` 规范化：scheme/host 小写，默认端口省略（`http:80` / `https:443`）。
- 禁止尾斜杠、路径、查询。
- 比较为**字符串相等**，不做通配（`https://*.example.com` 在规范中不是合法回显值）。
- `Origin: null` 永不匹配 `*` 以外任何值；`*` 与 `credentials=include` 互斥（A3）。

### 1.4 确定性要点

- 同一组 header 以不同书写顺序输入，输出必须字节一致：所有集合类字段先归一再去重再排序。
- `notes` 的两个必含键始终出现（即使为 `false`），避免"字段时有时无"。

## 二、T2 `cors_simulate_fetch`

### 2.1 输入

T1 全部字段 + `mode` + `redirects[]`（每项 `{url, status, headers}`）。

### 2.2 逐跳算法

```
hop 0: 原始请求（url）
for each redirect in redirects:
    hop += 1
    判定当前 hop 的响应是否允许重定向（3xx 可读；否则视为终止）
    若跨源（origin != redirect.url 的 origin）:
        events += origin_set_to_null      # 仅当 mode == cors 且 credentials == include 的规范情形见 2.3
        events += credentials_dropped
    以 redirect.url 为新的请求 URL，继续
final hop: 按 T1 分支做最终判定
```

### 2.3 `events[]` 的顺序与条件（固定）

- `origin_set_to_null`：跨源重定向发生时追加，**每发生一次追加一次**（不折叠）。
- `credentials_dropped`：跨源重定向且 `credentials == include` 时追加。
- 顺序 = 发生顺序；同为一步内触发时，`credentials_dropped` 先于 `origin_set_to_null`? **否** —— 定稿为 `origin_set_to_null` 在前（Origin 置空是该 hop 的第一步），`credentials_dropped` 在后。该顺序写进 golden case，不得临场决定。
- `no-cors` / `same-origin` 模式下不产生 `origin_set_to_null`（该模式下请求不带可比较的 Origin 语义），只按各自可见性规则产出判定。

### 2.4 `visible_headers[]`

- `mode == cors`：响应头 ∪ `Access-Control-Expose-Headers`（大小写不敏感匹配；`*` 在 credentials=include 时不展开）。
- `mode == no-cors`：`[]`（opaque）。
- `mode == same-origin`：全部响应头（同源）。
- 输出前统一小写 + 去重 + 排序。

### 2.5 `preflight_cache_key`

- 派生：`sha256(origin + "\n" + canonical_url)` 的**前 16 位 hex**，其中 `canonical_url = scheme://host[:port]`（无路径）。
- M1 已落进 `data/README.md` §4.7（含机器可读代码块），并由 `gen_codes.py` 渲染进 `codes.json`；审阅口径以那里为准。
- 不读时钟、不含随机盐。

### 2.6 `max_age_effective`

- 取 `Access-Control-Max-Age` 的非负整数；缺失或非法 → `0`；超过规范上限（浏览器实现上限属实现差异）**不做裁剪**，只回显声明值。T2 无 `notes` 字段；`max_age_capped_by_client` 只存在于 T1 的 `notes`，恒为 `false`。

## 三、T3 `cache_evaluate`

### 3.1 算法（RFC 9111 §4.2 / §4.2.1 / §4.2.3）

```
C1  now = parse(now)；stored.stored_at = parse(...)；缺失/非法 → INVALID_TIME_FORMAT
C2  no-store → action = miss, reasons += CACHE_NO_STORE（短路，不再计算新鲜度）
C3  response_date = Date 头（缺省用 stored_at）
C4  apparent_age = max(0, response_time - date_value)
C5  corrected_age_value = Age 头（缺省 0，非法按 0 + CACHE_INVALID_AGE）
C6  corrected_initial_age = max(apparent_age, corrected_age_value)
C7  resident_time = now - response_time
C8  current_age = corrected_initial_age + resident_time
C9  freshness_lifetime：
      s-maxage > max-age > Expires-Date > heuristic(10% of Date-Last-Modified, 上限 24h)
      无 Last-Modified 时启发式值为 0，并记 CACHE_HEURISTIC_FRESHNESS
C10 is_fresh = current_age < freshness_lifetime
C11 action：
      no-cache → revalidate（无论是否 fresh）
      is_fresh → serve
      stale 且 must-revalidate → revalidate（CACHE_MUST_REVALIDATE_STALE）
      stale 且在 stale-while-revalidate 窗口内 → serve + CACHE_STALE_WHILE_REVALIDATE
      否则 → revalidate（CACHE_AGE_EXCEEDS_LIFETIME）
```

### 3.2 边界与陷阱

- `max-age` 非整数 / 负数 → `CACHE_INVALID_MAX_AGE`，该指令按**不存在**处理（继续看 `Expires`）。
- `Expires` 早于 `Date` → `CACHE_EXPIRES_IN_PAST`，新鲜期为 `0`。
- `Age` 大于新鲜期 → 必然 stale（不因 `Age` 大而跳过计算）。
- `stale-while-revalidate` 窗口：`current_age - freshness_lifetime <= swr` 时仍在窗口内；窗口外必须 `revalidate`。
- **不读系统时钟**；`now` 缺失 → `INVALID_INPUT`（不给默认值）。
- 全部计算用整数秒；`Age` 与 `max-age` 比较用整数，不引入浮点。

### 3.3 输出

`freshness_lifetime` / `current_age` / `is_fresh` / `action` / `stale_while_revalidate_window` / `must_revalidate` / `reasons[]`。
`reasons[]` 每条带 `spec_ref`（RFC9111 条款号，M1 逐条核对后登记）。

## 四、T4 `conditional_evaluate`

### 4.1 求值顺序（RFC 9110 §13.2.2，固定短路）

```
E1  If-Match 存在：
      "*" 且资源存在 → 通过；否则按强比较逐个 ETag 比对
      不匹配 → 412，rule_applied = if_match
E2  If-Match 不存在且 If-Unmodified-Since 存在：
      资源 last_modified > 该日期 → 412，rule_applied = if_unmodified_since
E3  If-None-Match 存在（优先于 If-Modified-Since）：
      "*" 且资源存在 → 304（GET/HEAD）或 412（其它方法）
      弱比较命中 → 304/412，rule_applied = if_none_match
E4  If-None-Match 不存在且 If-Modified-Since 存在（仅 GET/HEAD）：
      资源未在该时间之后修改 → 304，rule_applied = if_modified_since
E5  以上都不适用 → 200，rule_applied = none
```

### 4.2 比较函数（两个，不共用）

| 函数 | 规则 | 用于 |
| --- | --- | --- |
| `strong_compare(a, b)` | 两侧均非 `W/`，且 opaque-tag 逐字节相等 | `If-Match` |
| `weak_compare(a, b)` | 剥离 `W/` 后 opaque-tag 相等 | `If-None-Match` |

- opaque-tag 含引号，比较时**保留引号**做逐字节比较。
- 解析 `W/` 前缀只允许恰好一个；`w/` 小写视为非法（按普通 tag 处理会导致错误匹配 → 应报 `INVALID_HEADER_VALUE`）。该判定写进 golden case。
- `If-None-Match` 用弱比较 → `weak_comparison_used = true`；`If-Match` → `false`。
- `Last-Modified` 只做秒级比较，按 HTTP-date 解析；解析失败 → 条件**被忽略**并记 `COND_IGNORED_INVALID_DATE`。

### 4.3 `explain[]`

- 固定模板 + 参数渲染，一条 `code` 对应一条固定文案；不生成自然语言。
- 顺序：按 `code` 字典序（与其他 tool 的集合类字段一致），`detail` 内参数按出现顺序。

## 五、T5 `vary_match`

### 5.1 算法

```
V1 解析 cached.vary（逗号拆分、trim、小写、去重、排序）→ normalized_vary
V2 若含 "*" → match = miss，reasons += VARY_STAR_NEVER_MATCHES（短路）
V3 对 normalized_vary 的每个字段：
      取 cached 存储时值与 incoming 值的归一形式
      缺失 = 空串（不区分"没有"与"空值"）
      归一：trim + 内部连续空白折叠为单空格 + 大小写策略（字段类型表）
      不等 → differing_headers += 字段
V4 differing_headers 非空 → miss + VARY_FIELD_MISMATCH；否则 hit
```

### 5.2 归一化策略表（按字段类型，写进 `codes.json` 旁表）

| 字段类型 | 策略 |
| --- | --- |
| 大多数 header | trim + 空白折叠；**值大小写敏感** |
| `Accept` / `Accept-Encoding` / `Accept-Language` | 值大小写**不敏感**，逗号分段后排序（顺序不影响协商结果） |
| `User-Agent` | 大小写敏感，仅 trim |
| 字段名 | 永远小写 |

- 策略表是**数据**，不是代码分支；M1 落进 `references/codes.json` 的 `vary_normalization` 段。
- `VARY_FIELD_MISSING`：仅在"一侧有、另一侧缺失"时追加（即使最终值恰好都为空，也要标注，便于解释 miss 原因）。

### 5.3 输出

`match` / `differing_headers[]` / `normalized_vary[]`；后两者按 `data/README.md` §4.3 排序。

## 六、tool 输出与 schema 的字段集合等式

- 每个 tool 有一份 JSON Schema（`schemas/tools/<name>.json`），`output` 段声明**全部**字段、`required` 列出**始终出现**的字段。
- 守门测试：跑全部 golden case，收集实际输出键集合 → 与 schema `properties` 键集合**相等**（不是包含）。
- `additionalProperties: false` 写进 schema；实现中不允许多余键。
- schema 与实现的字段集合相等是 M5 DoD 的硬门。

## 七、错误路径的统一落法

| 输入问题 | tool 面 error.code | 备注 |
| --- | --- | --- |
| 缺必填字段 / 类型错 | `INVALID_INPUT` | `field` 指明哪一项 |
| 时间不可解析 | `INVALID_TIME_FORMAT` | 不回退系统时钟 |
| header 名非法 | `INVALID_HEADER_NAME` | token 字符集 |
| header 值非法（如 ETag 引号不配对） | `INVALID_HEADER_VALUE` | 不猜测性修复 |
| 方法不在允许集合 | `UNSUPPORTED_METHOD` | 大小写不敏感匹配后 |

- 错误结果形如 `{"error": {"code": ..., "field": ..., "detail": "<固定模板>"}}`，**`detail` 也是模板**。
- 任何错误路径都不得写出半个结果对象；不得写盘。
